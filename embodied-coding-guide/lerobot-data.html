01 · DATA MODEL

LeRobot 格式先记四个层级

面试中不要只背目录。先解释四个抽象层级，再落到 v3 文件。

v3 的核心变化

v2.x 常见“一条 episode 一个 Parquet/MP4”；v3 将多条 episode 合并进较大的 file-xxx.parquet/mp4，再用关系型 episode metadata 恢复边界。收益是文件更少、初始化和流式读取更适合大规模数据；代价是不能再用“文件边界就是 episode 边界”的旧假设。

02 · VERSION EVOLUTION

LeRobot v2.1 与 v3.0：逻辑不变，物理存储重构

两代格式都表达 observation、action、timestamp、task 和 episode；最大差异不是模型输入，而是 episode 如何映射到文件和 metadata。

v2.1 · Episode-based
dataset/
├─ meta/
│  ├─ info.json
│  ├─ episodes.jsonl
│  ├─ episodes_stats.jsonl
│  └─ tasks.jsonl
├─ data/chunk-000/
│  ├─ episode_000000.parquet
│  └─ episode_000001.parquet
└─ videos/chunk-000/<camera>/
   ├─ episode_000000.mp4
   └─ episode_000001.mp4

一条 episode 对应一个低维 Parquet；每个相机也为该 episode 保存一个独立 MP4。chunk 主要用于限制单目录文件数量。

v3.0 · File-based
dataset/
├─ meta/
│  ├─ info.json
│  ├─ stats.json
│  ├─ tasks.parquet
│  └─ episodes/chunk-000/file-000.parquet
├─ data/chunk-000/file-000.parquet
└─ videos/<camera>/chunk-000/file-000.mp4

一个 Parquet/MP4 可以连续存放多条 episode。每条 episode 在共享文件中的行区间、视频起止时间和分片位置由关系型 metadata 恢复。

对比维度v2.1v3.0工程影响
核心组织episode-based：文件边界≈episode 边界file-based：多条 episode 合并到可配置大小的文件v2.1 直观；v3 显著减少海量小文件
低维数据episode_XXXXXX.parquet，一条轨迹一个文件file-XXX.parquet，一个文件含多条轨迹v3 读取单条 episode 必须利用行区间 metadata
视频数据每个 camera × episode 一个完整 MP4每个 camera 的共享 MP4 分片，episode 对应其中连续时间段v3 按文件与 timestamp seek；删除/抽取轨迹不能只删一个 MP4
任务表tasks.jsonltasks.parquet语义仍是 task string ↔ task index，序列化方式改变
episode 基本信息episodes.jsonl：index、tasks、lengthmeta/episodes/*.parquet：基本信息 + data/video 定位和时间范围v3 metadata 承担关系索引职责
episode 统计episodes_stats.jsonl 为每条轨迹保存 feature 统计episode Parquet 中可包含展平的 per-episode stats；stats.json 保存全局聚合统计迁移后必须核对 action/state 统计维度和值域
info.jsonversion、fps、features、规模、splits、episode 路径模板和 chunk 配置保留全局 schema，并增加/更新 file-based data/video 路径和文件大小配置两版都先通过 codebase_version 识别格式，不能只看目录猜版本
扩展性数据大时 episode × camera 产生大量小文件面向百万 episode、内存映射和 Hub streaming官方文档报告 v3 初始化可快约 3–5 倍；实际收益依数据和存储而定
单条轨迹操作复制/删除对应 Parquet 与 MP4 较直接需要按 metadata 切片，必要时重写 Parquet 或重新编码混合视频分片v3 更适合批量工具，不宜手工移动文件
模型侧接口加载后仍可得到相似的 sample dict 与 delta_timestamps 时间窗模型通常不应依赖底层文件布局，但数据脚本和可视化器必须区分版本
最关键的一句话

v2.1 把“episode”同时作为逻辑轨迹和物理文件单位；v3.0 只保留它作为逻辑单位，物理层改为较大的 file shard，再用 metadata 建立 episode → Parquet 行区间 / MP4 时间区间的映射。

MIGRATION

v2.1 迁移到 v3.0 不能只看转换脚本成功

迁移改变存储和索引，不应改变任务语义、episode 顺序、连续值或视频对齐。

# 当前官方迁移入口；实际使用前以所安装 LeRobot 版本为准
python src/lerobot/scripts/convert_dataset_v21_to_v30.py \
  --repo-id your_id/existing_dataset
迁移阶段必须检查通过标准
迁移前备份或保留原 revision；记录 v2.1 的 episode/frame/task 数、feature schema、fps 和文件清单原数据可回滚，统计口径有基准
结构检查codebase_version、总数、camera keys、dtype/shape/names、data/video 路径除格式字段外，schema 与 v2.1 语义一致
逐 episode 对账随机与边界 episode 的 length、task、首末 state/action、timestamp数值一致，episode 无丢失、重排或串接
视频对账首帧/中间帧/末帧、总帧数、fps、camera 对应关系和 seek 时间画面与同一时刻 state/action 保持同步
统计量对账action/state 的 min/max/mean/std、维度 names、图像统计键是否满足训练配置无缺 key、NaN、形状变化或异常尺度
训练冒烟加载多个 episode、构造历史观测和 action chunk、跑一个 batch forward/loss窗口不跨 episode，padding/mask 正确，loss 有限
转换不会自动修复语义问题

v2.1 中若动作单位、坐标系、相机名称、时间戳或 commanded/executed action 本来就定义不清，转换到 v3 后仍然不清。迁移工具解决的是序列化与索引，不是标定、同步和动作语义。

45 秒版本对比回答

LeRobot v2.1 是 episode-based，一条轨迹对应一个 Parquet，每个相机对应一个 episode MP4，episode、任务和统计量分别存在 JSONL metadata 中；优点是直观、单条轨迹易操作，缺点是大规模数据会产生海量小文件。v3.0 改为 file-based，把多条 episode 合并到较大的 Parquet 和 MP4 分片，用 Parquet episode metadata 记录行区间、文件索引和视频时间范围，同时使用 tasks.parquet 与全局 stats.json。模型看到的 observation/action 逻辑基本不变，但底层加载、抽取、删除和迁移工具必须理解新版关系索引。

03 · V3 METADATA

metadata 保存的是“如何解释和定位数据”

以下聚焦 v3.0；它通常不保存所有图像和每帧连续值，那些在 data/ 与 videos/ 中。

v3 组件典型内容训练用途常见误解
info.json全局数据契约codebase version、robot type、fps、总帧/episode/task 数；每个 feature 的 dtype、shape、维度名称；data/video 路径模板和分片配置；视频编码信息构建输入输出 schema，确定相机键、动作维度和文件位置它说明“有什么、长什么样”，不等于说明每一维的物理控制语义
stats.json全局统计量各连续 feature 的 count、mean、std、min、max，以及版本支持的分位数等统计训练归一化；推理时用同一统计量反归一化 action不能在 train/val/test 全部数据上重算，否则可能泄漏；也不能把不同动作语义的数据盲目共用统计量
tasks.parquet任务词表自然语言 task 与整数 task_index 的映射任务条件训练，减少每帧重复字符串的存储早期 v3 文档或 v2.x 可能写 tasks.jsonl；当前 v3 代码以 Parquet 为准
meta/episodes/*.parquet每条轨迹索引episode_index、length、tasks、dataset 起止行；data/video 的 chunk/file index、帧/时间偏移；每 episode 统计和附加 metadata恢复 episode 边界、按 episode 切分、定位共享分片中的帧和视频v3 一个物理文件可以含多条 episode，不能按文件名直接计算 episode 数
60 秒标准回答

LeRobot v3 的 metadata 是数据集的数据契约和关系索引。info.json 描述全局 schema、fps、规模和分片路径；stats.json 保存各 feature 的统计量供归一化；tasks.parquet 把语言任务映射到 task index；meta/episodes 保存每条 episode 的长度、任务、全局行区间以及对应 data/video 分片和时间偏移。真正逐帧的 state、action 和 timestamp 在 Parquet，图像在 MP4。v3 允许多个 episode 共用一个文件，所以必须依赖 metadata 恢复逻辑边界。

metadata 还缺什么才可复现？

动作是关节位置、末端绝对位姿还是增量？角度单位、坐标系、夹爪正负方向、commanded/executed action、外参版本、延迟与过滤流程。这些应写进数据卡、feature names 或自定义字段，不能期待一个 [8] shape 自动表达。

为什么 stats 是系统契约？

训练和推理若使用不同统计量，模型看到的输入分布与输出尺度会改变。最危险的故障是 action 反归一化错误：离线 loss 正常，真机却速度或位移异常，因此 checkpoint、schema 和 stats 必须绑定版本。

04 · FRAME TO WINDOW

策略训练读取的不是孤立一帧

典型样本是短历史观测和未来动作块，边界处还要处理 padding 与有效掩码。

sample(t) = { ot+Δo, at+Δa, task, pad_mask }
delta_timestamps = {
    "observation.images.front": [-0.20, -0.10, 0.00],
    "observation.state":        [-0.20, -0.10, 0.00],
    "action":                   [ 0.00,  0.05, 0.10, ..., 0.75],
}

dataset = LeRobotDataset(repo_id, delta_timestamps=delta_timestamps)
字段作用检查方法错误后果
timestampepisode 内物理时间，连接不同模态与视频帧单调性、间隔分布、跳变与重复值视觉和动作错位，模型学到错误因果关系
episode_index防止窗口跨越两次独立轨迹边界前后 task、frame index 是否重置把上一条结尾和下一条开头拼成假轨迹
frame_indexepisode 内离散顺序从 0 连续递增、与 length 一致丢帧不易定位，视频 seek 与表格错位
action监督未来机器人命令或执行量范围、速度/加速度、单位、与 state 的关系动作语义混乱比模型结构错误更致命
pad_mask标记 episode 边缘重复/填充出来的时间步loss 是否只在有效位置计算模型过度学习静止尾帧或虚假重复动作
按秒定义窗口

不同数据源的频率不一致时，H=16 本身没有统一物理含义；16 步在 20 Hz 是 0.8 s，在 50 Hz 只有 0.32 s。跨数据源混训时先统一控制频率，或用秒级 delta_timestamps 表达同一时间范围。

06 · UMI

UMI 最重要的不是“没有机器人”

真正的关键是把人类示范变成可迁移的机器人策略接口。

PORTABLE INTERFACE

手持夹爪缩小形态差距

操作者在真实环境中直接演示，设备保留机器人夹爪的交互方式，并用腕部相机记录第一视角。

ROBUST TRACKING

恢复 6DoF 末端轨迹

UMI 对快速运动下的 SLAM 做专门设计；轨迹质量决定动作标签质量，也是公开流程中最脆弱的环节。

POLICY INTERFACE

相对轨迹 + 延迟匹配

用相对末端轨迹减弱全局坐标和机器人本体差异，并在推理时匹配观测与执行延迟。

如果只答一个重点为什么重要缺失会怎样
任务空间相对轨迹表示把“人手设备的绝对世界位姿”转换成“从当前末端出发的未来变化”，使数据更接近机器人可执行的统一接口策略容易记忆采集坐标原点与场景布局，跨环境和跨本体迁移困难
准确 6DoF 追踪动作标签本身由追踪恢复，pose 漂移会直接污染监督视觉看起来正确但 action target 错，BC 会忠实学习噪声轨迹
观测/执行延迟匹配训练和部署必须保持相同的“图像对应未来哪段动作”的因果关系动态任务中系统性相位滞后，表现为追不上、过冲或动作顿挫
一句话回答

UMI 的价值是用便携手持设备规模化采集“接近机器人末端执行器”的人类示范，并通过准确位姿追踪、相对轨迹动作表示和推理延迟匹配，把这些非本体数据变成可迁移到不同机器人上的视觉运动策略。

30 Hz UMI + 20 Hz 真机怎么做？

选择 20 Hz 的公共时刻；UMI 位姿在这些时刻插值，旋转用 SLERP，视频选曝光中心最近帧；动作转换为相对于当前末端的未来轨迹。训练和部署都以相同秒级 observation/action horizon 构造窗口，并根据真机感知到执行延迟整体平移 action target。

仅按最近邻够吗？

慢速准静态任务可能够；快速接触和双手协同通常不够。需要量化最近邻时间残差、端到端延迟和采样 jitter，并用接触/夹爪事件检查相位。对高频信号应先低通或提取窗口特征。

如果实际做过说明工具、指标和发现

“我把相对末端轨迹变到机器人 base frame，用连续 seed 做离线 IK，并在 Rerun/RViz/MoveIt 中叠加末端和关节轨迹；主要检查 IK 成功率、位姿残差、关节速度及碰撞。”

如果只做过轨迹可视化不要把它说成完成 IK

“我已完成坐标变换和 3D 轨迹可视化，用于检查方向、尺度和连续性；尚未把全量轨迹经过带碰撞约束的 IK 验收，这是下一步。”

如果尚未做过给出可执行验证方案

先离线抽取轨迹、统一坐标，使用 Pinocchio/MoveIt 求 IK；统计可达率、残差和速度违约，再可视化失败区间，最后低速空载回放。

10 · GENERATIVE POLICY

Diffusion 与 Flow Matching：都从噪声生成动作

区别主要在训练目标、概率路径和推理方程；不要回答成“一个加噪，一个不加噪”。

维度Diffusion PolicyFlow Matching Policy
核心对象通常学习噪声 ε、score ∇log p 或 diffusion velocity直接回归概率路径上的向量场 ut(x|c)
前向路径按噪声 schedule 逐渐破坏数据，常对应 SDE/离散 Markov 链可选多种条件概率路径；最常见直线/OT 路径从噪声连接数据
训练随机 timestep 构造带噪动作，回归 ε/score/v随机 t 构造 xt，回归该处目标速度；无需训练时模拟 ODE
采样反向 SDE/ODE 或 DDIM 等迭代去噪从噪声出发积分 ODE：dx/dt=vθ(x,t,c)
步数经典实现步数较多，现代 solver/蒸馏可显著减少直线路径常更直、可用较少 ODE 步，但并非天然“一步”
共同优势能表达多峰、连续、高维 action chunk；比单点 MSE 更不容易平均多种合理动作
最小公式

直线 Flow：xt=(1−t)ε+ta，监督速度 u=a−ε，优化 ‖vθ(xt,t,c)−u‖²；推理从 x₀∼N(0,I) 积分到 x₁。Diffusion 则常用 εθ(xt,t,c) 回归加入的噪声，再按反向过程逐步恢复动作。

面试中的严谨表述

Flow Matching 是训练连续归一化流的向量场回归方法，兼容包括 diffusion path 在内的多类概率路径；因此二者不是完全互斥的两个集合。机器人论文里常把“DDPM 风格 ε-prediction”与“直线/OT Flow Matching”作工程对比。

12 · ATTENTION

公式、√dk 与多头复杂度

这类题先写 shape，再解释统计量和计算量。

Attention(Q,K,V)=softmax(QKT/√dk)V
为什么除以 √dk？

若 q、k 每一维近似独立、均值 0、方差 1，则点积 q·k 是 dk 项之和，方差约为 dk，标准差约为 √dk。除以 √dk 后 logit 尺度保持 O(1)，避免维度增大时 softmax 过度饱和、梯度变小。

Q、K、V 分别是什么？

Q 表示当前 token 想检索什么，K 表示每个 token 提供怎样的匹配索引，V 是匹配后真正被加权聚合的信息。Self-Attention 的 Q/K/V 来自同一序列的不同线性投影；Cross-Attention 的 Q 与 K/V 来自不同序列。

项目多头注意力面试解释
原理把 dmodel 投影成 h 组 Q/K/V，每头在 dk=dmodel/h 子空间独立 attention，拼接后再乘 WO不同头可以学习位置、物体、语言、状态、动作时序等不同关系
优势并行关注多种关系和表示子空间；比单头在同一总维度上更有结构化表达能力不是简单“重复 h 次”，各头有独立投影参数
投影复杂度Q/K/V/O 约 O(B·L·d2)短序列且 d 大时，这部分可能占主要计算
注意力复杂度score + weighted sum 约 O(B·L2·d)虽然有 h 个头，但每头维度是 d/h，总渐进量级不多乘一个 h
注意力显存显式 attention matrix 约 O(B·h·L2)长序列瓶颈通常来自 L²；FlashAttention 改善实际 IO/显存，不改变全连接 attention 的数学依赖
具身联系

图像 patch、语言 token、本体 state、触觉 token 和动作 token 可通过 Self/Cross Attention 融合。真正工程问题还包括：各模态 token 数差异、时间戳是否对齐、是否需要 causal mask，以及高频触觉是否应先压缩再进入慢速 VLA。

14 · INTERVIEW FLASHCARDS

自变量一 / 二面十问速答

每题先用黑体结论回答，再根据面试官追问进入上方章节。

Q1 · LeRobot metadata 保存什么？v2.1 和 v3 有何不同？

都保存解释数据所需的 schema、任务和 episode 信息，但序列化与定位职责不同。 v2.1 使用 info.json、episodes.jsonl、episodes_stats.jsonl 和 tasks.jsonl，文件本身按 episode 划分；v3 使用 info.json、stats.json、tasks.parquet 和 meta/episodes Parquet，由后者定位共享 Parquet/MP4 中的每条轨迹。

Q2 · Diffusion 和 Flow Matching 有什么区别？

Diffusion 常回归噪声/score 并求解反向扩散；Flow Matching 直接回归概率路径上的速度场并积分 ODE。 二者都可生成多峰连续动作；FM 可使用 diffusion path，因此理论上并非完全互斥。

Q3 · π₀.₅ 相比 π₀ 改了什么？

重点从通用灵巧控制扩展到开放世界泛化。 π₀.₅ 加入异构 co-training、高层子任务和 Web/语言数据；先用 FAST action token 预训练，后训练再加入 Flow Action Expert，同一模型执行高低层推理。

Q4 · π₀.₅ 用了多少数据、训练多久？

公开的是约 400 小时移动操作数据，外加更多其他机器人与非机器人数据；主训练为 280k 预训练步 + 80k 后训练步。 完整混合数据总小时数、硬件规模和墙钟训练时间未公开。

Q5 · 力扣简单题怎么准备？

优先覆盖哈希、双指针、栈、BFS/DFS 和一维 DP。 每题训练 20 分钟内写完、三组样例 dry run，并主动说明复杂度与边界；详见算法题页。

Q6 · Attention 公式，为什么除以 √dk？

softmax(QKT/√dk)V；缩放是为了稳定 logit 方差。 独立单位方差分量的点积方差随 dk 增长，除以 √dk 避免 softmax 饱和和梯度过小。

Q7 · 多头注意力原理、优势和复杂度？

多个独立投影子空间并行做 attention，再 concat + WO。 优势是同时建模多类关系；投影约 O(Ld²)，attention 约 O(L²d)，显式权重显存约 O(hL²)。

Q8 · UMI 和真机时间尺度不同怎么对齐？

按原始 timestamp 映射到统一物理时间轴，而不是按 frame index。 位置插值、旋转 SLERP、视频最近邻、高频触觉先低通/聚合；使用相同秒级窗口，并补偿真机感知—推理—执行延迟。

Q9 · 怎么利用失败数据？

先标注失败类型和发生时刻，再为不同目标选择训练方式。 可训练成功/奖励模型、保留有效前段、收集接管恢复、做偏好或 offline RL；没有 outcome 条件时不要把整条失败轨迹等权加入 BC。

Q10 · UMI 最重要什么？试过 IK 和轨迹可视化吗？

核心是可迁移的策略接口：可靠 6DoF 追踪、相对末端轨迹和延迟匹配。 IK 是落到具体机器人的可执行性检查；只陈述实际完成部分，并补充应检查可达率、位姿残差、关节速度/限位、碰撞和 3D 轨迹回放。

个人信息脱敏边界

公开复习页只保留技术机制。面试回答项目时可以说设备类别、数据契约、同步/标定方法、自己负责的模块和公开结果；不要展示内部数据规模、传感器序列号、网络地址、供应商报价、代码路径、未发布模型效果或他人贡献。无法公开的数字可回答“内部数据不便披露，但我可以说明统计口径和验证方法”。
